Proxmox qcow2 Image Building

Difficulty: Advanced · Estimated time: 40 min

This lesson presents two parallel approaches for building a Proxmox VE qcow2 image. Approach A is the OpenStack SDK Python pipeline (Proxmox VE 8.2): an automated workflow that drives a temporary build instance from Python and uploads the result to OpenStack Glance.

Approach B is the manual KVM/QEMU bare-metal build (Proxmox VE 9.2): you build a generic golden image by hand, import it into Glance, and deploy it to bare metal through OPCP/Ironic. Choose Approach A for a hands-off, scripted build, or Approach B when you need full control over a reusable bare-metal image.

Approach A — OpenStack SDK pipeline

Overview

This lesson covers the Python SDK approach for building Proxmox VE qcow2 disk images on OVH OpenStack. The pipeline orchestrates a multi-step workflow: create a temporary SLES build instance, download the Proxmox ISO, convert it to qcow2 format using qemu-img, create a snapshot, and upload the final image to OpenStack Glance.

By the end of this lesson, you will understand how to automate the entire image building process using the OpenStack SDK Python API and the build-image CLI subcommand.

Prerequisites

  • OpenStack credentials (application credentials or username/password)
  • Python 3.9+ with openstacksdk installed
  • An SSH key pair registered in OpenStack
  • Access to a SLES base image in OpenStack Glance
  • Familiarity with Baremetal Provisioning concepts

Step-by-step Workflow

The image building pipeline executes these steps in order. Each step uses the OpenStack SDK for Python to interact with cloud services.

Step 1: Create Build Instance

A temporary compute instance is created from a SLES base image. This instance serves as the build environment where the ISO will be downloaded and converted. The instance name follows the format proxmox-installer-{unix_timestamp}. 

import time
import openstack

# Connect using application credentials
conn = openstack.connect(cloud='ovh')

# Create the build instance
timestamp = int(time.time())
server = conn.compute.create_server(
    name=f"proxmox-installer-{timestamp}",
    image_id=conn.compute.find_image("SLES 15 SP5").id,
    flavor_id=conn.compute.find_flavor("b2-30").id,
    networks=[{"uuid": conn.network.find_network("Ext-Net").id}],
    key_name="my-key"
)

# Wait for the instance to become ACTIVE (timeout: 600s)
server = conn.compute.wait_for_server(server, wait=600)

Step 2: Download Proxmox ISO

Once the instance is active and SSH connectivity is established, the Proxmox ISO is downloaded to the build instance. The download is performed via SSH command execution with integrity verification based on expected file size. 

import paramiko

# Connect via SSH to the build instance
ip_address = server.access_ipv4
ssh = paramiko.SSHClient()
ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy())
ssh.connect(ip_address, username="sles", key_filename="~/.ssh/id_rsa")

# Download the Proxmox ISO
iso_url = "https://download.proxmox.com/iso/proxmox-ve_8.2-1.iso"
download_cmd = f"wget -q -O /tmp/proxmox.iso {iso_url}"
stdin, stdout, stderr = ssh.exec_command(download_cmd, timeout=1800)
exit_status = stdout.channel.recv_exit_status()

if exit_status != 0:
    raise RuntimeError(f"ISO download failed: {stderr.read().decode()}")

# Verify file size integrity
stdin, stdout, stderr = ssh.exec_command("stat -c %s /tmp/proxmox.iso")
actual_size = int(stdout.read().decode().strip())
assert actual_size == expected_size, "ISO integrity check failed"

Step 3: Convert ISO to qcow2

The downloaded ISO is converted to qcow2 format using qemu-img convert. This produces a disk image compatible with OpenStack Glance. 

# Convert ISO to qcow2 format on the build instance
convert_cmd = "qemu-img convert -f raw -O qcow2 /tmp/proxmox.iso /tmp/proxmox.qcow2"
stdin, stdout, stderr = ssh.exec_command(convert_cmd, timeout=600)
exit_status = stdout.channel.recv_exit_status()

if exit_status != 0:
    error_output = stderr.read().decode()
    raise RuntimeError(f"Conversion failed: {error_output}")

# Verify output file exists and has content
stdin, stdout, stderr = ssh.exec_command("stat -c %s /tmp/proxmox.qcow2")
qcow2_size = int(stdout.read().decode().strip())
assert qcow2_size > 0, "qcow2 output file is empty"

Step 4: Create Server Snapshot

A server snapshot captures the state of the build instance, including the converted qcow2 file. The snapshot name follows the format proxmox-{version}-{YYYYMMDD-HHMMSS}. 

from datetime import datetime, timezone

# Create a snapshot of the build instance
build_time = datetime.now(timezone.utc).strftime("%Y%m%d-%H%M%S")
snapshot_name = f"proxmox-8.2-{build_time}"

snapshot_id = conn.compute.create_server_image(
    server.id,
    snapshot_name
)

# Wait for the snapshot to become ACTIVE
image = conn.image.wait_for_status(
    conn.image.get_image(snapshot_id),
    status="active",
    wait=1800
)

Step 5: Upload to Glance

The final qcow2 image is uploaded to OpenStack Glance with the appropriate metadata. Once uploaded, it becomes available as a bootable image in your project. 

# Upload the qcow2 image to Glance
image = conn.image.create_image(
    name="proxmox-ve-8.2-qcow2",
    disk_format="qcow2",
    container_format="bare",
    visibility="private",
    proxmox_version="8.2",
    build_timestamp=datetime.now(timezone.utc).isoformat()
)

# Upload the image data
conn.image.upload_image(
    image,
    data=open("/tmp/proxmox.qcow2", "rb")
)

# Wait for the image to reach ACTIVE status
image = conn.image.wait_for_status(image, status="active", wait=1800)
print(f"Image uploaded: {image.id} — {image.name}")

Configuration Reference

The build pipeline is configured via a YAML file. Below is the full schema with all available parameters: 

# image-build-config.yaml
image_build:
  iso_url: "https://download.proxmox.com/iso/proxmox-ve_8.2-1.iso"
  base_image_name: "SLES 15 SP5"
  flavor_name: "b2-30"
  target_image_name: "proxmox-ve-8.2-qcow2"
  proxmox_version: "8.2"
  target_visibility: "private"        # private | shared | public
  build_timeout: 1800                 # seconds (60–7200)
  iso_expected_size: 1200000000       # bytes (optional)
  iso_download_dir: "/tmp"
  iso_download_timeout: 1800
  conversion_timeout: 600
  snapshot_timeout: 1800

openstack:
  auth_url: "https://auth.cloud.ovh.net/v3"
  region: "GRA9"
  auth_type: "v3applicationcredential"
  application_credential_id: "${OS_APPLICATION_CREDENTIAL_ID}"
  application_credential_secret: "${OS_APPLICATION_CREDENTIAL_SECRET}"

instance:
  ssh_key_name: "my-key"
  ssh_key_path: "~/.ssh/id_rsa"
  network_name: "Ext-Net"
ParameterRequiredDefaultDescription
iso_urlYes—HTTPS URL to Proxmox ISO file
base_image_nameYes—SLES image name in Glance
flavor_nameYes—Compute flavor for build instance
target_image_nameYes—Name for the final qcow2 image
target_visibilityNoprivateImage visibility (private/shared/public)
build_timeoutNo1800Build timeout in seconds (60–7200)
iso_expected_sizeNo—Expected ISO size in bytes for verification
iso_download_dirNo/tmpDownload directory on build instance

CLI Usage

The build-image subcommand triggers the full pipeline from the command line. It integrates with automation scripts and CI/CD pipelines. 

# Run the full image build pipeline
proxmox-automation build-image --config image-build-config.yaml

# Validate configuration without building (dry run)
proxmox-automation build-image --config image-build-config.yaml --dry-run

Exit codes:

  • 0 — Build completed successfully (image ID printed to stdout)
  • 1 — Build or configuration failure (error message on stderr)

Example output on success:

Image built successfully:
  ID:   a1b2c3d4-e5f6-7890-abcd-ef1234567890
  Name: proxmox-ve-8.2-qcow2

Approach B — Manual KVM/QEMU bare-metal build

Overview & architecture

The objective is to build a generic, reusable Proxmox VE whole-disk qcow2 golden image, import it into OpenStack Glance, and deploy it to physical servers through OPCP / Ironic bare metal. A single image can then provision many Proxmox servers.

The image uses a GPT partition table, UEFI boot, and keeps the system disk separate from future data disks. Server-specific settings — hostname, IP addresses, network interfaces, bridges and bonds, Proxmox cluster, ZFS / Ceph storage, and Corosync — are applied after deployment, not baked into the golden image.

The end-to-end pipeline:

Proxmox VE ISO
      |
      v
+---------------------------+
| Temporary KVM/QEMU VM     |
|   UEFI                    |
|   8 vCPU                  |
|   16 GB RAM               |
|   64 GB qcow2 disk        |
+-------------+-------------+
              | Proxmox installation
              v
+---------------------------+
| proxmox-opcp.qcow2        |
|   GPT                     |
|   EFI                     |
|   Debian                  |
|   Proxmox VE              |
+-------------+-------------+
              | Glance import
              v
+---------------------------+
| OPCP / OpenStack / Ironic |
+-------------+-------------+
              |
              v
       Bare Metal Server

Use the standard x86_64 / amd64 build for Intel Xeon or AMD EPYC servers (for example proxmox-ve_9.2-1.iso). The ARM64 version is only for servers with an ARM64 processor.

Prerequisites

The build host runs Debian or Ubuntu and provides the full KVM/QEMU toolchain: QEMU, libvirt, virt-install, and qemu-img, together with UEFI / OVMF firmware support. KVM hardware acceleration is strongly preferred so the temporary build VM runs at near-native speed.

Install the required packages:

apt update
apt install -y qemu-utils qemu-system-x86 libvirt-daemon-system libvirt-clients virtinst ovmf

Confirm the key tools are available:

qemu-img --version
virsh --version
virt-install --version

Prepare the Proxmox ISO

Copy the Proxmox VE 9.2 installer ISO into the libvirt images directory so the build VM can mount it, set read permissions so libvirt can access it, and verify the file is in place: 

cp proxmox-ve_9.2-1.iso /var/lib/libvirt/images/
chmod 644 /var/lib/libvirt/images/proxmox-ve_9.2-1.iso
ls -lh /var/lib/libvirt/images/proxmox-ve_9.2-1.iso

Create the 64 GB qcow2 disk

Create the 64 GB system disk that will hold the Proxmox installation, then inspect it to confirm the format and virtual size: 

qemu-img create -f qcow2 /var/lib/libvirt/images/proxmox-opcp.qcow2 64G
qemu-img info /var/lib/libvirt/images/proxmox-opcp.qcow2

The qemu-img info output should report the expected format and size:

file format: qcow2
virtual size: 64 GiB

This 64 GB disk is the Proxmox system disk only. Future data disks, ZFS pools, or Ceph disks must not be included in this image — they are provisioned separately after the node is deployed.

Create the build VM

Create a temporary build VM with 8 vCPU, 16 GB RAM, and UEFI boot, attaching the VirtIO qcow2 disk and a VirtIO network adapter, and booting from the Proxmox VE 9.2 installer ISO: 

virt-install \
  --name proxmox-image-builder \
  --memory 16384 \
  --vcpus 8 \
  --cpu host \
  --os-variant debian13 \
  --disk path=/var/lib/libvirt/images/proxmox-opcp.qcow2,format=qcow2,bus=virtio \
  --cdrom /var/lib/libvirt/images/proxmox-ve_9.2-1.iso \
  --network network=default,model=virtio \
  --boot uefi

If a dedicated host bridge is available, attach the build VM to it instead of the default libvirt network. Replace the default network option: 

--network network=default,model=virtio

with the bridge option:

--network bridge=br0,model=virtio

Install Proxmox VE

Install Proxmox VE normally from the installer ISO. For a bare-metal golden image, choose UEFI boot, a GPT partition table, an ext4 / LVM filesystem, and the VirtIO disk as the installation target: 

Boot       : UEFI
Partition  : GPT
Filesystem : ext4 / LVM
Disk       : VirtIO disk

Use a simple system-disk layout: an EFI partition plus an LVM volume holding the root, swap, and data logical volumes. 

/dev/vda
 |
 +-- EFI
 |
 +-- LVM
      |
      +-- root
      +-- swap
      +-- data

Avoid ZFS for the template system disk; physical storage disks are configured after the server is deployed.

Generic configuration (network, hostname, no cluster)

The image must stay generic because interface names differ between the build VM (for example ens18) and the final server (for example eno1 or ens1f0np0). Before finalizing the template, reduce /etc/network/interfaces to a minimal loopback-only configuration: 

auto lo
iface lo inet loopback

The final network configuration (management interface, vmbr0 bridge, bonds, VLANs, and the storage, cluster, and migration networks) is applied after deployment.

The template must not use a final server name. Set a neutral template hostname: 

hostnamectl set-hostname pve-template

After deployment each node gets its final name (pve01, pve02, …) and /etc/hosts is updated accordingly.

The build image must not be joined to a Proxmox cluster. Do not configure Corosync, the Proxmox cluster, Ceph, shared storage, or remote nodes in the template. The cluster is created only after the servers are deployed.

Clean the image

Before the final shutdown, remove all instance-specific data so the golden image stays generic. Each deployed node then regenerates its own identity on first boot.

Remove the SSH host keys. They are regenerated automatically on the next boot, so every deployed node gets a unique set: 

rm -f /etc/ssh/ssh_host_*

Reset the machine ID so each node obtains its own identifier, and keep the D-Bus machine-id pointing at it: 

truncate -s 0 /etc/machine-id
rm -f /var/lib/dbus/machine-id
ln -s /etc/machine-id /var/lib/dbus/machine-id

Clear any DHCP leases captured during the build: 

rm -f /var/lib/dhcp/*

Rotate and vacuum the journal, then drop rotated log archives: 

journalctl --rotate
journalctl --vacuum-time=1s
rm -f /var/log/*.gz

Finally, clean the APT package cache: 

apt clean

Shut down and remove the temporary VM

With the image cleaned, shut the build VM down cleanly so the filesystem is flushed and the qcow2 disk is left in a consistent state: 

shutdown -h now

Once the VM has stopped, /var/lib/libvirt/images/proxmox-opcp.qcow2 is the finished Proxmox system image. Remove the libvirt definition of the build VM without deleting the qcow2 disk. Never pass any option that removes storage volumes, or you will destroy the image you just built: 

virsh undefine proxmox-image-builder --nvram

Verify and compress the image

Check the image integrity and inspect it so you know the qcow2 file is consistent and see its size, format, and backing details: 

qemu-img check /var/lib/libvirt/images/proxmox-opcp.qcow2
qemu-img info /var/lib/libvirt/images/proxmox-opcp.qcow2

Optionally create a compressed copy for faster upload and more compact storage, then verify the compressed result: 

qemu-img convert -O qcow2 -c /var/lib/libvirt/images/proxmox-opcp.qcow2 /var/lib/libvirt/images/proxmox-opcp-final.qcow2
qemu-img check /var/lib/libvirt/images/proxmox-opcp-final.qcow2

Test the image

Before importing the image into OPCP, boot the finalized image without the ISO attached to confirm it boots on its own: 

virt-install \
  --name pve-test \
  --memory 8192 \
  --vcpus 4 \
  --disk path=/var/lib/libvirt/images/proxmox-opcp-final.qcow2,format=qcow2 \
  --import \
  --boot uefi \
  --network network=default,model=virtio

The system must boot directly, with no ISO required. A successful boot follows this chain: 

UEFI
 |
 v
GRUB
 |
 v
Debian Kernel
 |
 v
Proxmox VE

Import into OpenStack Glance

Import the finalized image into Glance so OPCP / Ironic can use it to provision bare-metal servers: 

openstack image create "Proxmox-VE-9-Baremetal" \
  --disk-format qcow2 \
  --container-format bare \
  --file /var/lib/libvirt/images/proxmox-opcp-final.qcow2

Verify the image was registered correctly:

openstack image show Proxmox-VE-9-Baremetal

The key properties should be as follows:

disk_format      = qcow2
container_format = bare
status           = active

The image must be used as a whole-disk image. Do not associate it with a kernel_id or ramdisk_id.

Bare-metal UEFI configuration and deployment

The target physical server must boot in UEFI mode. In Ironic, the node must use boot_mode:uefi, and the server firmware must be set to UEFI boot. 

boot_mode:uefi
openstack baremetal node show <UUID>

Deploy through OpenStack:

openstack server create \
  --flavor <flavor-baremetal> \
  --image Proxmox-VE-9-Baremetal \
  --network <network-id> \
  pve01

The deployment workflow proceeds as follows:

Post-deployment, recommendations and evolution

Once a node boots from the golden image, apply the node-specific configuration. Because the same image serves many physical servers, these settings are what make each node unique: 

hostname
management IP address
DNS
NTP
vmbr0 bridge
network bonds
VLANs
storage
Proxmox cluster

Recommendations. Keep the golden image generic. Build in only what every server shares, and leave anything server-specific for post-deployment.

Include in the image:

  • Proxmox VE
  • Debian
  • EFI partition
  • Bootloader
  • Standard packages
  • Common administration tools

Do not include in the image:

  • Final IP address
  • Final hostname
  • Hardware-dependent NIC configuration
  • Network bonds
  • Final bridges
  • Proxmox cluster
  • Corosync
  • Ceph
  • Data ZFS pool
  • Server-specific configuration

Recommended evolution. A first-boot configuration mechanism can further automate deployment, applying the hostname, network, DNS, NTP, bridges, bonds, and storage automatically on first boot. It can be implemented with:

  • cloud-init
  • A first-boot systemd script
  • Ansible
  • Terraform
  • An OPCP orchestration mechanism
